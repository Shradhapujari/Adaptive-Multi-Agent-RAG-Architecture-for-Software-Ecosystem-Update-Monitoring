# Q&A prep — 2026-09-24 review

Anticipated follow-ups, grounded in `FINDINGS.md` and current run state as of 2026-09-23.

## "So does multi-agent beat the single agent or not?"
No, on retrieval. Findings 5, 8, 11 all land the same way: leak-free, one-pass,
frozen — every arm is at nDCG@3 0.30 (Finding 8) or 0.49 (Finding 11 after the
cascade fix), and the arms are indistinguishable. The one real, reproducible
effect this project found is a *failure mode*: the query rewriter replacing
the user's query destroys retrieval (Finding 4), which is fixable and cheap.
Say that plainly — don't reach for the retry arm to rescue the story, it isn't
measured yet (see below).

## "What happened to the +17.2% / +0.044 headline numbers?"
Both withdrawn, and say why in one line each:
- +17.2%: rested on a bespoke score standard IR metrics contradict (Finding 1).
- +0.044: a record-vs-replay artifact — the multi-agent arm was scored against
  a live corpus that drifted between record and replay; frozen and single-pass
  it's null (Finding 11, formerly Finding 9's tier-prior framing).

## "What's the retry arm's status — is it a fourth finding of no difference?"
Not yet measurable, and don't call it null. It was *structurally* unreachable
(quality floors always exceeded threshold — Finding 12), fixed 2026-09-23
(`f66c639`, `83a56e8`) to read the pre-floor overlap signal. Offline replay
says it would fire on 13% of 500 questions at threshold 0.15. The one-pass
`marag_llm` vs `marag_llm_retry` comparison is queued behind the b1000
baseline and hasn't run. If asked "when will you know" — honestly: it starts
as soon as b1000 finishes or is deprioritized; no fixed ETA.

## "Why is the b1000 baseline run paused?"
Deliberate, not stuck — SIGSTOP'd (PID 42307) to free the machine for this
demo; two evals never run concurrently on this host. It resumes with
`kill -CONT`, not a relaunch, so no work is lost. At last check it was at
499/1000.

## "Why do the arms keep coming out identical — is something broken in the harness?"
No — it's the corpus and the pooling, not a bug. Two independently confirmed
mechanisms: (1) cross-system judge pooling is always on regardless of the
`judge_pool` flag (read `run_eval.py`, not the flag name), so arms scored
apart vs. together give different numbers purely from pool width (Finding 10
demonstrated a +0.055 recall swing from pool width alone, before it was
identified as a cross-run artifact in Finding 11). (2) the benchmark's own
Reddit-sourced questions were retrieving their own source post before the
2026-09-17 fix (own-post leak) — most pre-fix absolute scores above ~0.3 are
this, not real retrieval quality.

## "Is any of this comparison actually frozen/reproducible?"
Only `replay`/`strict` runs are. `record` runs — including the cited clean
500 (`run_1789703506`) — are internally valid but externally irreproducible
because the live document pool drifts day to day. The b100_clean snapshot
specifically has been mutated by warm replays backfilling it, so don't cite
it as frozen; any new ablation needs a fresh corpus dir.

## "What about the n=300 / n=10 / yes-no results — do those change the story?"
- n=300: retrieval parity holds; the faithfulness gap is entirely the answer
  format confound (template vs. prose), not content (Finding 6). Not a frozen
  comparison — quote medians, not means (format confound skews the mean).
- n=10 inversion: p=0.016 is the statistical floor with only 7 nonzero pairs,
  not evidence of a strong effect — report it as the floor, not a result.
- yes/no eval: all four tested sets are in-sample; no claim survives
  out-of-sample yet. A fifth, frozen set is the prerequisite before citing this.

## "What's actually going into the paper as of today?"
Section on retry (`sec:retry`) now says "reachable, unmeasured" rather than
structurally null — that's the only paper change from today's commit
(`83a56e8`). The core claims are Findings 1–9 as summarized in
`sec:results-summary`; nothing new is confirmed for the headline result this
week.
